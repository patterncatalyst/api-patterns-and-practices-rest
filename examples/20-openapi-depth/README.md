# Ch20 — OpenAPI in depth

OpenAPI has moved past being "a Swagger file with a few extra keywords." As
of OpenAPI 3.1, the `components.schemas` section **is** JSON Schema (the
2020-12 dialect) — no translation layer, no `nullable: true` workaround for
a field that can be absent or `null`. The spec also grew first-class
support for **webhooks**: a top-level section describing calls the *server*
makes *out* to a client-registered callback URL, documented with the exact
same request/response machinery as a regular path.

This chapter proves both capabilities are real, servable things — not just
spec trivia — and pairs them with a **living-contract drift check**: the
booking shape declared in each stack's served OpenAPI document has to keep
agreeing with the shared contract (`contracts/schemas/shipping.schema.json`)
or `verify.sh` fails.

Like Ch4, this example runs a trimmed Booking resource (create + fetch
only — the full create/read/list/cargo/replace/patch/delete sequence
already lives in `examples/04-contract-first`). The point here is the
**served OpenAPI document**, not the resource's CRUD surface.

## Run it

```bash
cd examples/20-openapi-depth
./verify.sh
```

This brings both services up with `docker compose`, waits for health, and
for **each** stack:

1. fetches the OpenAPI document from its native path and asserts `200` +
   valid JSON;
2. runs `check_openapi.py`, which asserts the document contains a
   JSON-Schema-style nullable construct (a `type` array including `"null"`,
   or OAS-3.0's `nullable: true`) **and** a non-empty top-level `webhooks`
   section;
3. **drift check**: asserts the document's own `Booking` schema declares
   the same SET of `required` property names as `#/$defs/Booking` in
   `contracts/schemas/shipping.schema.json` — normalized, not a byte-equal
   diff (see "The drift probe" below);
4. drives a live `POST /bookings` → `GET` round trip and schema-validates
   both response bodies against `#/$defs/Booking`.

Prints `PASS` only if all of the above holds for both stacks.

To poke at it by hand instead:

```bash
docker compose up --build

# The served OpenAPI documents:
curl -s 'http://localhost:8100/q/openapi?format=json' | jq .   # Quarkus
curl -s http://localhost:8020/openapi.json | jq .              # FastAPI

# Both declare a `type`-array nullable field and a `webhooks` section:
curl -s 'http://localhost:8100/q/openapi?format=json' | jq '.components.schemas.Booking.properties.cancellationReason, .webhooks'
curl -s http://localhost:8020/openapi.json | jq '.components.schemas.Booking.properties.cancellationReason, .webhooks'

# A real create -> read round trip:
curl -s -X POST -H 'Content-Type: application/json' \
  -d '{"origin":{"unLocode":"USNYC"},"destination":{"unLocode":"NLRTM"},"cargo":[{"description":"x","type":"GENERAL","dimensions":{"weightKg":10}}]}' \
  http://localhost:8100/bookings | jq .

docker compose down -v
```

Ports are **unique** across the repo's examples: Quarkus on `8100`→8080,
FastAPI on `8020`→8000 (Ch20's reserved pair).

The Grafana LGTM observability stack is opt-in and off by default (neither
app ships telemetry yet):

```bash
docker compose --profile observability up --build
```

## How each stack serves a modern OpenAPI document

**Quarkus**: MicroProfile OpenAPI's annotation model has no clean way to
author a top-level `webhooks` section or a `type`-array nullable property
today, so this chapter serves a **hand-authored static document**
(`quarkus/src/main/resources/META-INF/openapi.yaml`, OpenAPI 3.1) instead of
one generated by scanning `@Path`-annotated resources.
`application.properties` sets `mp.openapi.scan.disable=true`, which tells
`quarkus-smallrye-openapi` to serve that static file **verbatim** at
`/q/openapi` rather than merging it with the generated model (the default
behavior) — see the Quarkus `openapi-swaggerui` guide's "Loading OpenAPI
Schema From Static Files" section. `BookingResource.java` still serves real,
working `POST`/`GET /bookings` endpoints completely independent of this
flag; the static document and the live resource are deliberately decoupled
in this example (the static doc's schema is illustrative, not reflective of
JAX-RS annotations).

**FastAPI / Python**: FastAPI natively supports OpenAPI 3.1 and top-level
`webhooks` (pass an `APIRouter` to the `webhooks=` constructor argument —
see `python/app/main.py`'s `webhooks_router`). What it does **not** do by
default is emit a `type`-array nullable for an `Optional[...]` pydantic
field — pydantic v2's JSON Schema export renders that as
`anyOf: [{...}, {"type": "null"}]`, which is valid JSON Schema but not the
`type`-array *form* this chapter is specifically demonstrating. `main.py`
wires a `custom_openapi()` function onto `app.openapi` that calls FastAPI's
own `get_openapi()` (so paths/schemas still reflect the real routes —
`response_model=Booking` is set on the create/fetch routes purely so
`components.schemas.Booking` exists in the generated document; both routes
still return a `JSONResponse` directly, which FastAPI passes through
unvalidated) and then patches one illustrative field
(`cancellationReason`) onto the generated `Booking` schema with an explicit
`"type": ["string", "null"]`.

Both stacks add the **same** illustrative field for this purpose —
`cancellationReason`, described identically in both — to make the parallel
obvious. It appears **only** in the served OpenAPI documents, never in a
real response body: the shared contract's `#/$defs/Booking` has
`additionalProperties: false` and does not declare it, so adding it to an
actual response would fail `validate_response.py`'s schema validation. The
documents also both declare a `bookingStatusChanged` **webhook** carrying a
`BookingEvent`-shaped payload (mirroring `#/$defs/BookingEvent` in the
shared schema) — neither app ever actually issues that call; it exists
purely so a real `webhooks` section renders.

## The drift check: why "normalized," not byte-equal

A served OpenAPI document and the shared contract schema will never be
byte-identical — different `$id`s, different descriptions, different
structuring of `$ref`s. Byte-equal diffing would make this check so brittle
it would start failing on harmless wording changes, which trains people to
ignore (or delete) the gate. Instead, `check_openapi.py` compares the **SET
of required property names** declared for `Booking` in each stack's live
document against `#/$defs/Booking.required` in
`contracts/schemas/shipping.schema.json` — a structural comparison that
only fails when the two have genuinely drifted apart on *which fields a
booking must have*, which is the thing an API consumer actually depends on.

## The drift probe

To see each assertion actually catch something, break it on ONE stack and
re-run `./verify.sh`:

**1. Drop a required field from the drift check (Quarkus).** In
`quarkus/src/main/resources/META-INF/openapi.yaml`, under
`components.schemas.Booking.required`, delete `cargo`:

```yaml
required: [id, status, origin, destination, createdAt]   # cargo removed
```

Re-run `./verify.sh`:

```
  - quarkus: Booking required-field set DRIFTED from the contract.
      contract  (#/$defs/Booking.required): ['cargo', 'createdAt', 'destination', 'id', 'origin', 'status']
      live doc  (components.schemas.Booking.required): ['createdAt', 'destination', 'id', 'origin', 'status']
      missing from live doc: ['cargo']
      extra in live doc:     []
```

Revert the line and re-run — back to `PASS`.

**2. Delete the nullable construct (either stack).** In
`quarkus/src/main/resources/META-INF/openapi.yaml`, delete the
`cancellationReason` property entirely from `components.schemas.Booking`
(or, on the Python side, delete the `booking_schema["properties"][...]`
block in `python/app/main.py`'s `custom_openapi()`). Re-run `./verify.sh`:

```
  - quarkus: no JSON-Schema nullable construct found anywhere in the served
    OpenAPI document (expected a `type` array containing "null", or
    `nullable: true`)
```

**3. Delete the webhooks section (either stack).** Delete the top-level
`webhooks:` block from `META-INF/openapi.yaml`, or stop passing
`webhooks=webhooks_router` to `FastAPI(...)` in `python/app/main.py`.
Re-run `./verify.sh`:

```
  - python: served OpenAPI document has no non-empty top-level `webhooks`
    section (got: None)
```

**4. Note what does NOT break the gate.** Flip `cancellationReason`'s
`type: [string, 'null']` to the OAS-3.0 `nullable: true` style — the
nullable-construct check accepts either form, so `verify.sh` still passes.
That's deliberate: the point of the check is "does this document express
nullability in a JSON-Schema-recognizable way," not "does it use the exact
3.1 spelling."

All three breaks are isolated to one file each; revert them and `./verify.sh`
returns to `PASS`.

## Endpoints

| Method | Path | Behavior |
|---|---|---|
| POST | `/bookings` | Create a booking (same shape/quote formula as Ch4). |
| GET | `/bookings/{id}` | Fetch a booking. |
| GET | `/q/openapi?format=json` (Quarkus) / `/openapi.json` (Python) | The served OpenAPI 3.1 document this chapter is about. |
| GET | `/health` (Python) / `/q/health` (Quarkus) | Liveness, used by `docker compose` healthchecks. |
