# Ch15 — Large binary resources & Range requests

A booking's **manifest** is a large binary document — not a small JSON
payload. This chapter shows the pattern for serving that kind of resource
over HTTP: a known, fixed size up front (`HEAD`), the full body on a plain
`GET`, and a byte-range slice of it via `Range`/`206 Partial Content`/
`Content-Range` (RFC 9110 §14) — the mechanism every resumable download,
video scrubber, and PDF viewer's "jump to page" relies on.

- `contracts/openapi/shipping-api.yaml` — `/bookings/{bookingId}/manifest`
  (`HEAD`/`GET`, the `Range` request header, `Accept-Ranges`/
  `Content-Range` response headers).
- `contracts/schemas/shipping.schema.json` — unchanged from Ch4; the
  manifest's body is binary, not one of the JSON `$defs`.

Quarkus (`quarkus/`, port 8095→8080) and FastAPI (`python/`, port
8015→8000) each implement a thin Ch4-style Booking resource (`POST`/`GET`,
just enough to mint an id) plus the manifest endpoint, against an in-memory
store. `verify.sh` creates a booking on each stack, then drives the full
HEAD → full-GET → bounded-Range → open-Range → unsatisfiable-Range →
unknown-booking sequence and checks status codes, headers, and exact byte
counts — not just "did it return something".

## Run it

```bash
cd examples/15-range-requests
./verify.sh
```

This brings both services up with `docker compose`, waits for health,
drives the manifest sequence against `localhost:8095` (Quarkus) and
`localhost:8015` (FastAPI), and tears the stack down again. Prints `PASS`
only if every assertion holds for **both** stacks.

To poke at it by hand instead:

```bash
docker compose up --build

booking_id=$(curl -s -X POST localhost:8095/bookings \
  -H 'Content-Type: application/json' \
  -d '{"origin":{"unLocode":"USNYC"},"destination":{"unLocode":"NLRTM"},
       "cargo":[{"description":"Pallet","type":"GENERAL","dimensions":{"weightKg":1000}}]}' \
  | jq -r .id)

curl -sI "localhost:8095/bookings/$booking_id/manifest"                     # HEAD: size + Accept-Ranges
curl -s -o full.bin "localhost:8095/bookings/$booking_id/manifest"          # full body
curl -s -D- -o chunk.bin -H 'Range: bytes=0-1023' \
  "localhost:8095/bookings/$booking_id/manifest"                           # 206 Partial Content
curl -s -D- -o /dev/null -H 'Range: bytes=99999999-99999999' \
  "localhost:8095/bookings/$booking_id/manifest"                           # 416 Range Not Satisfiable

docker compose down -v
```

## The manifest

Each booking's manifest is a **deterministic, fixed-size, in-memory**
binary blob — no file on disk, no persistence. Both stacks derive it the
same way: chain SHA-256 digests seeded by the booking id
(`block[0] = SHA-256(bookingId)`, `block[n] = SHA-256(block[n-1])`),
concatenate until the target size is reached, and truncate to it
(`ManifestGenerator.java` / `app/manifest.py`). The result is generated
once per booking id and cached, so repeated Range requests against the same
manifest don't re-hash ~2 MiB on every call.

```
MANIFEST_SIZE_BYTES = 2 MiB (2,097,152 bytes)
```

The two stacks are **not** required to produce byte-identical manifests for
the same id — each has its own booking store and mints its own ids. What
matters is that each stack, independently, produces a manifest of a known,
fixed size and serves correct byte ranges over it; `verify.sh` captures
`TOTAL` from the `HEAD` response on each stack and checks every subsequent
`Content-Length`/`Content-Range` against that stack's own `TOTAL`.

The media type on both the full `GET` and a `206` is `application/pdf`
(matching the contract's declared example) even though the body is a
generated byte pattern, not a structurally valid PDF — this chapter's point
is the Range mechanism, not PDF generation.

## Range semantics implemented

| Request | Response |
|---|---|
| `HEAD /bookings/{id}/manifest` | `200`, `Accept-Ranges: bytes`, `Content-Length: TOTAL`, no body |
| `GET /bookings/{id}/manifest` (no `Range`) | `200`, full body, `Accept-Ranges: bytes`, `Content-Length: TOTAL` |
| `GET` with `Range: bytes=START-END` | `206`, `Content-Range: bytes START-END/TOTAL`, `Content-Length: END-START+1` |
| `GET` with `Range: bytes=START-` (open) | `206`, `Content-Range: bytes START-(TOTAL-1)/TOTAL` — everything from `START` to the end |
| `GET` with `Range: bytes=-N` (suffix) | `206` — the **last** `N` bytes |
| `GET` with a `Range` whose `start >= TOTAL` | `416 Range Not Satisfiable`, `Content-Range: bytes */TOTAL` |
| A malformed `Range` header | Ignored per RFC 9110 §14.2 — falls back to a full `200`, same as no `Range` at all |
| `HEAD`/`GET` for an unknown `bookingId` | `404`, `Problem` (`application/problem+json`) |

`416`'s body is intentionally minimal — the spec allows (but doesn't
require) a `Problem` body there, and the `Content-Range: bytes */TOTAL`
header alone is enough for a client to retry with a corrected range.

## The drift probe

The whole point of this chapter is that `verify.sh` actually distinguishes
a `206` from a `200`, and checks the exact `Content-Range` value — not just
"some success code came back". To see it happen, introduce one of these
edits and re-run `./verify.sh`:

**Option A — return `200` instead of `206` for a Range request.**

In `python/app/main.py`'s `get_manifest_endpoint`, in the branch that builds
the final `206` response, change:

```python
return Response(
    content=chunk,
    status_code=206,
    ...
)
```

to:

```python
return Response(
    content=chunk,
    status_code=200,  # BUG: should be 206 (Partial Content)
    ...
)
```

(Or in `quarkus/.../ManifestResource.java`'s `get()`, change
`Response.status(206)` to `Response.status(200)` in the equivalent branch.)

Re-run `./verify.sh`. It fails immediately on the bounded-Range assertion
for that stack:

```
lib.sh: FAIL — python GET manifest (Range 0-1023): expected HTTP 206, got 200
```

**Option B — emit a wrong `Content-Range` value.**

In the same branch, change the header to drop the `-1` (an off-by-one on
the end of the range):

```python
"Content-Range": f"bytes {start}-{end+1}/{total}",  # BUG: end is wrong
```

Re-run `./verify.sh`. The status code is still `206` (correct), but the
`Content-Range` assertion catches the drift:

```
lib.sh: FAIL — python GET manifest (Range 0-1023): expected Content-Range 'bytes 0-1023/2097152', got 'bytes 0-1024/2097152'
```

Revert the edit and re-run `./verify.sh` — it goes back to `PASS` for both
stacks. That round trip (break it, watch the gate catch it, fix it, watch
the gate go green again) is the thing worth internalizing: `200` vs `206`
and an exact `Content-Range` are both load-bearing parts of the contract, a
status code alone isn't enough to trust a Range implementation.
