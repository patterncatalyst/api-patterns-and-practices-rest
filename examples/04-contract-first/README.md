# Ch4 — Contract-first anchor

The reference both-stack implementation of the shipping/cargo Booking +
Cargo resource model. The contract — not either codebase — is the source of
truth:

- `contracts/openapi/shipping-api.yaml` — endpoints, status codes, headers.
- `contracts/schemas/shipping.schema.json` — the exact payload shapes
  (`Booking`, `Cargo`, `BookingCollection`, `Problem`, ...).

Quarkus (`quarkus/`, port 8080) and FastAPI (`python/`, port 8000)
independently implement the identical contract against an in-memory store
(no persistence yet — that lands once a later chapter needs it). `verify.sh`
drives the same create → read → list → add-cargo → replace → patch → delete
sequence against **both** stacks and schema-validates every response body,
not just its HTTP status code. That's the load-bearing correctness step
this chapter exists to teach: two independent implementations that both
satisfy one written contract will produce identical response shapes, and a
shared schema validator is what catches it the moment they don't.

## Run it

```bash
cd examples/04-contract-first
./verify.sh
```

This brings both services up with `docker compose`, waits for health,
drives the endpoint sequence against `localhost:8080` (Quarkus) and
`localhost:8000` (FastAPI), schema-validates every response, and tears the
stack down again. Prints `PASS` only if every assertion holds for **both**
stacks.

To poke at it by hand instead:

```bash
docker compose up --build
curl -s -X POST localhost:8080/bookings \
  -H 'Content-Type: application/json' \
  -d '{"origin":{"unLocode":"USNYC"},"destination":{"unLocode":"NLRTM"},
       "cargo":[{"description":"Pallet","type":"GENERAL","dimensions":{"weightKg":1000}}]}' | jq .
docker compose down -v
```

The Grafana LGTM observability stack is opt-in and off by default (neither
app ships telemetry yet):

```bash
docker compose --profile observability up --build
```

## The quote formula

`Booking.quote` (`#/$defs/Money`) is computed identically on both stacks so
their responses are byte-for-byte comparable, not just independently valid:

```
quote.currency = "USD"
quote.amount   = format(sum(cargo[].dimensions.weightKg) * 2.50, ".2f")
```

`amount` is always a **decimal string** (e.g. `"3001.25"`), per the schema —
never a JSON number (see the drift probe below for why that distinction is
load-bearing). Both implementations compute the sum/format independently
(`QuoteCalculator.java` / `app/quote.py`); the example payloads in
`verify.sh` use weights chosen to avoid binary-floating-point rounding edge
cases (e.g. `1200.5 * 2.50 = 3001.25` is exact in IEEE 754 double
precision), so this reference build sidesteps the question of whether
`String.format("%.2f", ...)` (Java, HALF_UP) and Python's `f"{x:.2f}"`
(round-half-to-even) agree on every input — they don't have to, for inputs
that land exactly on two decimal places.

## IDs

`Booking.id` / `Cargo.id` are ULID-shaped (`bkg_`/`crg_` + 26-char Crockford
Base32: 48-bit timestamp + 80-bit randomness), matching the schema's
`^bkg_[0-9A-HJKMNP-TV-Z]{26}$` / `^crg_[0-9A-HJKMNP-TV-Z]{26}$` patterns.
Generated by a small dependency-free helper in each stack
(`Ulid.java` / `app/ulid.py`) rather than a library, so the Containerfiles
stay minimal — a real project should use a vetted ULID package instead.

## Endpoints implemented (identically, in both stacks)

| Method | Path                      | Success | Notes |
|--------|---------------------------|---------|-------|
| POST   | `/bookings`               | 201     | `Location: /bookings/{id}`, body = `Booking` |
| GET    | `/bookings`               | 200     | `BookingCollection`; cancelled bookings hidden by default |
| GET    | `/bookings/{id}`          | 200/404 | `Booking` or `Problem` |
| PUT    | `/bookings/{id}`          | 200     | full replace, idempotent |
| PATCH  | `/bookings/{id}`          | 200/415 | `application/merge-patch+json` only (thin merge-patch; full JSON Patch is Ch7) |
| DELETE | `/bookings/{id}`          | 204     | soft-delete: status → `CANCELLED`, hidden from default list |
| GET    | `/bookings/{id}/cargo`    | 200     | array of `Cargo` |
| POST   | `/bookings/{id}/cargo`    | 201     | `Location`, body = `Cargo` |

Errors are always `Problem` (`application/problem+json`): 404 not found,
400 validation, 415 unsupported PATCH media type. `_links` (HATEOAS) is
intentionally omitted everywhere — that's Ch12.

## The drift probe

The whole point of this chapter is that `verify.sh` actually rejects a
response that drifts from the contract — not just a response that's merely
wrong in some other way. To see it happen, introduce one of these edits in
either stack and re-run `./verify.sh`:

**Option A — make `quote.amount` a JSON number instead of a string.**

In `python/app/quote.py`, change:

```python
amount = f"{total_weight_kg * _RATE_PER_KG:.2f}"
```

to:

```python
amount = round(total_weight_kg * _RATE_PER_KG, 2)  # BUG: number, not string
```

(Or in `quarkus/.../QuoteCalculator.java`, change the `Money` constructor
call to pass `totalWeightKg * RATE_PER_KG` boxed as a number instead of the
formatted string — same idea.)

Re-run `./verify.sh`. It fails at the very first `validate_body Booking`
call for that stack, with something like:

```
INVALID: body does not conform to #/$defs/Booking
  - quote/amount: 3001.25 is not of type 'string'
lib.sh: FAIL — body does not conform to #/$defs/Booking
```

**Option B — add an undeclared top-level field to `Booking`.**

In `python/app/main.py`'s `create_booking`, stuff an extra key into the
response before returning it, e.g. temporarily build the JSON by hand with
an added `"internalNotes": "debug"` key. Because
`contracts/schemas/shipping.schema.json`'s `Booking` has
`additionalProperties: false`, `verify.sh` fails the same way:

```
INVALID: body does not conform to #/$defs/Booking
  - (root): Additional properties are not allowed ('internalNotes' was unexpected)
```

Revert the edit and re-run `./verify.sh` — it goes back to `PASS` for both
stacks. That round trip (break it, watch the gate catch it, fix it, watch
the gate go green again) is the thing worth internalizing: the contract
schema is enforced mechanically, at the payload level, independent of
either language's own type system.
