# Diagrams

Each diagram is a paired `name.svg` (committed, embedded via the `excalidraw.html`
include) + `name.excalidraw` (editable source). Generate both with
`scripts/generate_diagram.py` (see `references/diagram-engine.md`). Catalogue them
here as you add them:

| Diagram | Chapter | What it shows |
|---|---|---|
| `00-lab-topology` | Ch0 — Prerequisites & the lab | Quarkus and FastAPI services both implementing one OpenAPI 3.1 contract and reading/writing one Postgres instance; CI schema-validates live responses; LGTM observability shown as an optional, dashed lane. |
| `01-rest-constraints` | Ch1 — APIs & patterns | RPC/verb-oriented vs Web API/resource-oriented contrasted, then the five REST constraints (client–server, stateless, cacheable, uniform interface, layered system), with uniform interface emphasized in amber as the one most APIs violate. |
| `02-decision-framework` | Ch2 — The API decision framework | The six decision axes (interaction shape, payload size, latency/real-time need, cacheability, client diversity, evolution needs) feeding a central "pick the pattern, style & transport" node. Reused as the Decision box in later chapters. |
| `03-resource-model` | Ch3 — Designing around resources | The Booking→Cargo aggregate, and how it's exposed as a collection (`/bookings`), an item (`/bookings/{id}`) and a sub-resource (`/bookings/{id}/cargo`); notes that resources are nouns and must not mirror DB tables. |
| `04-contract-first-flow` | Ch4 — Contract-first with OpenAPI 3.1 | One contract scaffolds both stacks; CI schema-validates live responses; the flow branches to a passing merge or a drift-detected build failure. |
| `05-idempotency-matrix` | Ch5 — HTTP methods & idempotency | A method × {safe, idempotent} grid for GET/HEAD/PUT/DELETE/POST/PATCH, each row placed against a concrete booking operation (e.g. `PUT /bookings/{id}` idempotent, `POST /bookings` not idempotent). |
| `06-content-negotiation` | Ch6 — Content negotiation & status codes | A request's `Accept`/`Content-Type` headers flowing into the server's negotiation step, branching to 200 OK (match), 406 Not Acceptable (Accept unsatisfiable), or 415 Unsupported Media Type (Content-Type unsupported); plus a map of the key status codes (200/201+Location/204/400/404/409). |
| `07-patch-vs-merge` | Ch7 — Partial updates with PATCH | JSON Patch (RFC 6902, an ordered array of op/path/value operations) vs JSON Merge Patch (RFC 7396, a partial object where `null` deletes a field) applied to the same Booking, each with its distinct media type (`application/json-patch+json` vs `application/merge-patch+json`). |
| `08-pagination-strategies` | Ch8 — Pagination | Offset/limit, keyset/cursor, and seek/after_id compared side by side by request shape, response shape, and behavior under writes; notes that `limit` is always capped server-side as a DoS guard. |
| `09-sub-resources` | Ch9 — Sub-resources & nesting | When to nest a sub-resource (`/bookings/{id}/cargo` — real, exclusive ownership) vs when not to (`/locations/{id}` — reference data reused across bookings), and the redundant-endpoint pitfall where one resource is reachable at two URL shapes that drift apart. |
| `10-async-lifecycle` | Ch10 — Async operations | The 202 Accepted → poll → 303 See Other lifecycle for a long-running confirmation: client POSTs, gets a `Location` to an operation resource, polls it while `RUNNING`, and is redirected to the real booking on completion; includes a cancel branch (`DELETE /operations/{opId}` → 204, state `CANCELLED`). |
| `11-job-lifecycle` | Ch11 — Rerunnable jobs | The configure/enable split for a server-owned `manifest-reconcile` job: a job definition resource (schedule) vs run records it produces, fired either by the scheduler on an interval or on demand; each run moves through `PENDING` → `RUNNING` → `SUCCEEDED`/`FAILED`. |
| `12-hateoas-state-machine` | Ch12 — HATEOAS | The booking response as a finite state machine: `PENDING` → `CONFIRMED` → `IN_TRANSIT` → `DELIVERED`, plus `CANCELLED`, each state showing only the `_links` valid from there (e.g. `PENDING` exposes `self`/`confirm`/`cancel`; `DELIVERED` exposes `self` only). |
| `13-soft-delete-purge` | Ch13 — Soft delete & purge | `DELETE` sets `CANCELLED`, writes an audit record, and hides the booking from default list queries while it stays addressable by id; a separate, retention-governed purge job later performs the actual hard delete, after which the resource 404s. |
| `14-versioning-strategies` | Ch14 — Versioning | URI, query-parameter, custom-header, and media-type versioning compared by where the version lives and the caching cost (`Vary`) each incurs, plus a v1-vs-v2 response shape diff (`price`/`cargoDescription` vs `quote`/`cargo[]`) showing why the version exists. |
| `15-range-request-sequence` | Ch15 — Large binary resources & `Range` | A client HEADs a manifest to learn size and range support (`Accept-Ranges: bytes`, `Content-Length`), pulls the first 1 MiB with a `Range` request (`206 Partial Content` + `Content-Range`), then sends an out-of-bounds range that the server rejects with `416 Range Not Satisfiable`. |
| `16-streaming-modes` | Ch16 — Streaming deep dive | Chunked transfer encoding, Server-Sent Events (`text/event-stream`), and NDJSON (`application/x-ndjson`) compared side by side — each delivering pieces incrementally over one open connection — with the best-fit use case for each (progressive download, live browser updates, bulk export). |
| `17-cross-protocol` | Ch17 — Cross-protocol choices | REST/SSE, WebSockets, webhooks, and gRPC compared by direction (client-pull / server-push / bidirectional), connection model, and best-fit use case for moving data, especially streams; REST/SSE held as the default in the accent. |
| `18-concurrency-model` | Ch18 — Back-end I/O concurrency | Quarkus blocking (thread-per-request worker pool, exhaustion risk) vs reactive/virtual threads, and Python's GIL-bound threadpool vs the asyncio event loop, both families shown serving the same DB and file I/O without parking a real OS thread on I/O. |
| `19-http2-http3` | Ch19 — HTTP/2 & HTTP/3 | HTTP/1.1's serial, head-of-line-blocked requests vs HTTP/2's multiplexed streams over one TCP connection (HPACK, still TCP-HOL-blocked) vs HTTP/3's independent streams over QUIC/UDP (QPACK, connection migration, 0-RTT); notes HTTP/3 coverage is tier-gated in CI. |
